# Recovery 12 — Computation, Logic & Automation

## The Big Picture

This Recovery Codex volume belongs to **Computing & Software**. Its job is to
preserve computation as a recoverable discipline: logic, algorithms, data,
encoding, programming, systems, security, automation, and the hardware
substrates that make symbolic work executable.

```
COMPUTATION, LOGIC, AND AUTOMATION

Computation is disciplined symbol manipulation made reliable.

LOGIC -------> ALGORITHM ---> DATA
truth, rule,    procedure      representation,
proof           that halts     record, state
   |              |              |
   v              v              v
PROGRAM ----> MACHINE ----> SYSTEM
instructions    substrate,     process, network,
and tests       memory, I/O    users, failure
   |              |              |
   v              v              v
SECURITY ---> AUTOMATE ---> TEACH
integrity,      repeated       readers who can
access, trust   reliable work  debug and reason

Do not preserve apps first.
Preserve computation's grammar, evidence, and repair.
```

---

## Minimum Viable Capability

A society has recovered this volume's core capability when it can teach logic,
write algorithms, encode data, build tables and ledgers, reason about state,
construct simple computing devices or use surviving ones safely, write and test
programs, protect records, automate repeated work, and debug failures.

```
logic -> algorithm -> data -> program -> machine -> system -> security -> teaching
```

## The Recovery Ladder

| Level | Recovery Task | What Must Survive |
|---|---|---|
| Remember | Computation is method, not device worship | logic, algorithm, data, state, test |
| Recognize | Identify encodings, procedures, machines, interfaces, failures | diagrams, source, protocols |
| Measure | Track correctness, complexity, storage, power, error, uptime | tests, logs, checksums |

## Layer 1: Logic, Algorithms, and Data

| Capability | Recovery Use | Failure If Lost |
|---|---|---|
| Boolean logic | switching, search, diagnosis | vague decision rules |
| Algorithm | repeatable procedure | folklore process |
| Data model | structured records | unreadable piles |
| Encoding | symbols to storage | lost meaning |
| Checksum | error detection | silent corruption |
| Complexity | cost awareness | impossible plans |
| State machine | protocols and workflows | inconsistent systems |

Rule:

```
procedure + representation + test = recoverable computation
```

---

## Layer 2: Machines, Power, and Substrate

| Substrate | Use | Caveat |
|---|---|---|
| Paper tables | durable computation aid | slow, copy errors |
| Abacus / slide rule | arithmetic | training needed |
| Mechanical calculator | repeated arithmetic | precision and repair |
| Relay logic | teachable switching | contact wear |
| Vacuum tube / transistor | electronic logic | power, materials |
| Microprocessor salvage | high capability | toolchain dependence |
| Networked machine | shared computation | security and power |

Hardware rule:

```
no software without power, storage, I/O, cooling, and maintenance
```

---

## Layer 3: Programming, Testing, and Debugging

Programs are records of intended behavior.

| Practice | Recovery Value |
|---|---|
| Pseudocode | language-independent algorithm memory |
| Source code | editable behavior |
| Tests | executable expectations |
| Version history | change memory |
| Logs | operational evidence |
| Documentation | interface for future maintainers |
| Code review | shared reasoning |

Debugging rule:

```
reproduce -> localize -> explain -> change -> test -> record
```

---

## Layer 4: Security, Trust, and Automation

Automation repeats mistakes at machine speed unless constrained.

| Risk | Countermeasure |
|---|---|
| Data corruption | checksums, backups, audit |
| Unauthorized access | identity, roles, least privilege |
| Malware / sabotage | provenance, isolation, review |
| Automation runaway | limits, alarms, manual stop |
| Model overtrust | validation, monitoring, human responsibility |
| Single copy | redundancy and migration |

Security rule:

```
protect integrity first; confidentiality and availability follow the mission
```

## Cargo-Cult Traps

| Trap | Why It Fails | Countermeasure |
|---|---|---|
| Preserve apps, not source | behavior cannot be repaired | source, docs, tests |
| Data without schema | records become opaque | human-readable models |
| Automation without stop | failure scales | limits and manual override |
| Security theater | locks without threat model | integrity, roles, audit |
| AI oracle | plausible errors become authority | validation and human judgment |

## Practical Reconstruction Sequence

```
1. arithmetic, logic, tables, and algorithms
2. data records with schema and provenance
3. checksums, backups, and indexes
4. pseudocode and source-code literacy
5. simple computing devices and test suites
6. operating procedures, logs, and debugging practice
7. secure roles, audit, and automation limits
```

## Decision Cheat Sheet

| If you need to... | Start With | Key Caveat |
|---|---|---|
| Preserve computation | Algorithms, data models, source, tests, docs | Devices die; methods travel |
| Trust data | Schema, provenance, checksum, backup, audit | Data without context is noise |
| Automate work | Stable process, tests, limits, manual stop | Automation amplifies errors |
| Rebuild software | Pseudocode, small language, tests, logs | Toolchains are dependencies |
| Secure a system | Integrity, roles, least privilege, recovery | Security must match threat |
| Teach computing | Logic, state, representation, debugging | Coding without models is brittle |

## Common Confusion Points

**Computation is older than computers** — Tables, algorithms, logic, and
procedures are computation too.

**Data is not self-explaining** — It needs schema, units, provenance, and
purpose.

**Automation is not judgment** — It executes a model under assumptions.

**Security is not secrecy alone** — Integrity and accountability often matter
first in recovery.
